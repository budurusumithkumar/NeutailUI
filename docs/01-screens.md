# Screen Inventory

Each screen lists: purpose, primary API calls, and status (In scope / Future).

## 1. Login
- **Purpose:** authenticate with email + password.
- **API:** `POST /api/v1/auth/login`.
- **Behavior:** on success, store `access_token` + `user` (from `LoginResponse`), redirect to Home. On `401`, show inline error from `ErrorResponse.message`.
- **Status:** In scope.

## 2. Home (user-specific)
- **Purpose:** personalized landing page after login. First thing the user sees every session.
- **API:** `GET /api/v1/customers/me/summary`, `GET /api/v1/auth/me` (identity confirm).
- **Content:** greeting with `display_name`; loyalty tier + points balance; preferred categories/colors/styles as chips; usual size / fit preference; a prominent "Chat with your stylist" CTA that creates a session (`POST /api/v1/sessions`) and navigates to Chat; cart summary widget (item count, from local cart state).
- **Status:** In scope — explicitly required by the user.

## 3. Chat (Agent Assistant)
- **Purpose:** the core interaction — free-text conversation with the agent backend, with structured results rendered alongside the reply.
- **API:** `POST /api/v1/chat` per turn (requires an active `session_id` from Home or auto-created on entry); optionally `GET /api/v1/sessions/{id}/context` to restore state on reload.
- **Content:** scrolling message list (user bubbles + assistant bubbles); assistant turns can inline-render a product carousel/grid (`ChatResponse.products`), a fit-result card (`ChatResponse.fit`), an upsell offer card (`ChatResponse.upsell`); a lightweight agent-activity strip (`ChatResponse.agent_activity`) showing which agents ran (e.g. "Styling Agent ✓ · Fit Agent ✓"); message input; "Add to cart" action on each product card; tapping a product can pass `selected_sku` on the next chat turn (for fit follow-ups, per the `fitFollowup` example in the contract).
- **Status:** In scope — the core screen.

## 4. Product Detail (modal or drawer, launched from a product card in Chat)
- **Purpose:** let the user inspect a recommended product before adding to cart — bigger image, price, available sizes, reason codes ("why we picked this"), and (if already fetched) the fit verdict.
- **API:** none new — hydrated entirely from the `ProductCard` / `FitResult` already in the chat transcript. Requesting fit for a size not yet evaluated sends a new chat turn with `selected_sku` + a message like "will size 12 fit me?".
- **Status:** In scope (can ship as a simple modal, not a separate route).

## 5. Cart
- **Purpose:** review items added from chat, adjust quantity/size, remove items, see subtotal.
- **API:** **none in the current contract** — client-side only, backed by `localStorage` behind a `CartRepository` interface (see [03-api-integration.md](03-api-integration.md) Gap #1) so it can be swapped for a real cart endpoint later.
- **Which scan runs (default = the original quick one):** the cart's "Measure my size" opens the **original quick shoulder-width scan** by default (`fit/ShoulderScanModal.tsx`): pose model only, ~40 steady frames (about 2 s), 3D shoulder-joint distance from the model's metric ("world") landmarks × 2.4 → chest → size; no face, height, torso, second scan or camera-level check. It is fast and smooth but cannot see chest or belly and its world scale drifts toward an average body, so one real XXL user read XS/S/M with it — treat its size as rough. The slower face-scale + torso scan described below (two agreeing scans, camera-level check, steadiness rules) is kept and reachable with `?scan=advanced` on the cart URL (`fit/AdvancedBodyScanModal.tsx`); it is tagged in git as `fit-v2-face-torso`. Calibration mode (`?calibrate=1`) works with either scan and labels each record with its `engine`.
- **Fit check (return-rate reduction):** a "Measure my size" popup (`fit/BodyScanModal.tsx`) estimates chest girth entirely from the camera — the user types nothing. They sit comfortably facing the camera (seated laptop distance, ~0.6–1 m) with both shoulders fully in frame and arms slightly away from their sides — nobody has to stand or step back — and hold still for ~25 stable frames (~1.5 s at 20 detections/s). Two MediaPipe models run per frame (`lib/faceLandmarker.ts`, `lib/poseLandmarker.ts`):
  1. **Real-world scale from the user's own face** (`fit/faceScale.ts`): the iris diameter (~11.7 mm) and the cheek-to-cheek face width (13.2 cm — one real frame read ~12.7 cm by the iris ruler, so the landmark width is narrower than full bizygomatic width) are used as rulers, blended (iris weighted up to 80% the more pixels it covers), giving cm-per-pixel at the face and — via an assumed webcam field of view — an approximate camera distance. That distance corrects the scale for the shoulders (~6 cm behind the cheek plane) and torso (~12 cm). (Webcams have no depth sensor and single-image depth models are only relative, so a face-sized ruler is the practical "depth".)
  2. **Outer shoulder width** (`fit/bodyGeometry.ts` `shoulderSample`): the pose model's shoulder landmarks sit at the joints, *inside* the true shoulder edge, so the width is read from the person-mask silhouette 2–8 cm below them (deltoid to deltoid). Rejected unless the shoulder joints are a plausible 27–52 cm apart and the outline extends past both — a real close-up (0.5 m, head and chest only) made both models guess: shoulder points landed 22 cm apart on the chest and the outline missed a whole shoulder, giving a bogus 37 cm. (An earlier "elbows must be visible" rule caught this too but forced people to stand up, so it was replaced.) A `SHOULDER_CLOTHING_ALLOWANCE_CM` is subtracted since the outline includes the shirt.
  3. **Torso width** (`torsoSample`): always the same fixed strip — 12–18 cm below the shoulder line (just under the armpits) — however far away the person sits, taking the median width of the rows that are not merged with an arm (rows wider than 96% of the outer shoulder outline count as arm-merged; fewer than 5 clear rows ⇒ the Arms clear check fails). A band that grew with the visible frame measured a different part of the body at every distance and was a cause of repeated scans disagreeing; the same synthetic body now reads 43.8–43.9 cm from 50 cm to 110 cm away. The strip must fit in the frame, otherwise the popup names a distance to move back to. It cannot see the belly, so a broad belly reads a little small.
  4. **Chest girth** (`fit/sizing.ts`): the torso strip width plus an estimated depth (`DEPTH_PER_WIDTH`, `DEPTH_OFFSET_CM`; a front view can't show thickness) give an ellipse girth (`GIRTH_ADJUST_CM` = -4 for the shirt). Shoulder width is no longer part of the chest estimate — it was the noisiest input (one person's outline read 42–63 cm across scans, ×2.4) — and is only a sanity check (joint/outline plausibility, arm-merge limit) and a displayed value. Mapped to a letter size on an Indian-style chart (S=36in … XXL=44in); sizes within 2 cm of a boundary report "XXL or XL" and both count as a good fit. The actual size is shown, not a range.
  5. **Two scans must agree** (`AGREE_WITHIN_CM` = 5, `MAX_SCANS` = 4): after a scan's readings are steady, the popup pauses ~3.5 s ("relax, then hold the same posture again") and scans again; a size is only shown when two scans give chest estimates within 5 cm of each other (the result is their mean, with "2 scans agreed"). A mismatch keeps the newer scan and asks for another; after 4 scans with no agreement it says "The scans wouldn't agree" and gives no size. During scanning a **posture guide** shows the one posture to hold for both scans: upright, shoulders level, hands resting on the lap, elbows slightly out, arms off the desk (forearms forward on the desk made the outline swing by ~20 cm).
  Each cart line then shows a verdict — **softer by design, since the estimate is only good to about a size**: Good fit (the estimated size, or the neighbouring one when within 2 cm of a boundary), "Close to your estimated size" (one step either way, never flagged), and only "Likely too small / too large" for sizes two or more steps away, which alone count towards the at-risk banner — with a one-tap "Switch to {size}" on those (limited to the item's `available_sizes` when known); a size dropdown and Remove are always available, and a banner counts items at return risk. Letter sizes (S/M/L, "Medium", "2XL") are compared on the chest chart, and UK numeric sizes ("12", "UK 12", 4–24) on a UK bust chart. Anything else ("EU 38", "32", "One Size") is shown as "Can't compare size …" with the raw value, rather than guessed at.
  - **History:** v1 took shoulder width from the pose model's "world" coordinates and was wrong by ~40 cm for a large-build user (those coordinates assume an average-sized body); v2 asked for a typed height plus full-body front and side poses at 2–3 m, impractical at a laptop; v3 (face scale + torso) hard-gated on distance and used joint-landmark shoulders. The current design comes from testing against a real webcam frame.
  - **Collecting readings:** judged over a sliding window of the latest 25 frames (so settling-in movement can't hold the scan back); the face-scale is smoothed with a short running median; frames are ignored while the face is growing/shrinking >4% (walking towards/away — the smoothed scale would lag and bias the size); agreement is IQR/median ≤ 12%, and after 12 s the latest window's median is accepted regardless, with a "readings varied" warning on the result. An earlier strict version (unbounded sample list, 8% agreement, no time limit) could measure forever without finalizing under real webcam noise.
  - **Sit-back gauge:** when the chest is out of frame the popup shows the current camera distance and the distance that would show it, with a small gauge (seated is fine — a real seated laptop user was at ~0.5 m, where the camera sees only ~37 cm of height, i.e. head, shoulders and ~14 cm of chest, so a torso measurement needs ~0.8–1 m). Perspective offsets between the cheek plane and the shoulder/torso planes were raised to 9/10 cm after that frame (people sit with the head forward of the shoulders).
  - **Chest required (product decision):** a size is only given when the chest is in view. Shoulder width alone cannot see chest or belly and swings with posture and distance (one real user's outline read 43.8 → 50.5 cm between 0.5 m and 0.8 m, and a true XXL read as XS/S/M), so there is no shoulders-only, "rough estimate" or account-profile fallback: if the chest is out of frame the popup shows a sit-back gauge (current distance, and the distance that would show it — seated is fine; a seated laptop user was at ~0.5–0.8 m where the camera sees only head, shoulders and ~14 cm of chest, and ~0.7 m is needed for the loosened 18 cm reach, ~1 m for the full band) and keeps waiting. The account's `usual_size` was tried as a fallback and dropped: it describes the account holder, not necessarily the person scanned (in the demo environment it is a fictional customer's size 12).
  - **Result frame:** the result shows the frame the size came from with the measured rows in green and the raw numbers (distance, face/iris px, outline shoulders, torso, steadiness) along the bottom, so a wrong size can be diagnosed from a screenshot. It is held in memory only and never uploaded.
  - **Calibration status:** the clothing allowances, face width and iris weighting were tuned after one real user reported an XXL being read as XXXL (outline shoulders 55 cm, chest ≈ 120); that is a single data point, not a validation.
  - **Speed:** measured on real models, a frame costs ~10 ms (face) + ~9 ms (pose) + ~3 ms (outline readback) at 1280×720, so compute is not the bottleneck; the slowness people felt in earlier versions came from strict gates (e.g. requiring the belly in frame) that kept the scan in a wait state.
  - **Measurement instability (why this feature is unproven):** one real user, same seat, scanned repeatedly and got chest estimates of ≈ 105, 124 and 90 cm (XL, XXXL, S) — far more spread than a size step (~5 cm). Arm position moves the outline a lot (53.9 cm arms down vs 61.1 cm hands on hips, which also let arm-contaminated rows through as torso). A guard that capped the outline at shoulder-joint distance + 12 cm was tried and reverted: the pose model placed that user's shoulder joints 30 cm apart (real ≈ 50 cm), so the cap collapsed the estimate to S/XS. A short band (< 30 cm below the shoulders) uses the median row width. None of this is validated against tape measurements, and no tape measurements have been supplied to calibrate against.
  - **Beta and calibration mode:** the popup and the cart banner are labelled **Beta**. Calibration mode (`?calibrate=1` on `/cart`, remembered on the device; `?calibrate=0` turns it off; off by default) adds a panel under a scan result to record the tape-measured truth next to the scan — chest (required), belly, shoulder width, usual T-shirt size, fitted/regular/loose, and who it is — saved with the scan's raw numbers (outline shoulder, adjusted shoulder, torso, estimated depth, joint distance, camera distance, face/iris px, band reach, spread) to `localStorage` (`neutail_calibration_v1`, this device only, never uploaded). "Copy all (JSON)", "Download CSV" and "Clear all" are provided. Purpose: collect tape-measured readings from ~10–20 different people, then fit the size formulas (`CHEST_*`, `DEPTH_*`, `TORSO_WEIGHT`, clothing allowances, `CHEST_UPPER_BOUND_CM`) to data instead of guessing. Code: `fit/calibration.ts`, `fit/CalibrationPanel.tsx`.
  - **No size from a shaky scan:** after the 12 s time limit, if the latest window's spread (the worse of shoulders and torso) is still above 20%, the popup says "We couldn't get a steady reading" with tips (sit upright, hands on the lap, good light) and gives no size — one real scan read ±35% and previously still produced XL/XXL. The live steadiness figure shows that same worse-of-two spread.
  - **Camera level + impossible-chest guard:** two agreeing scans read a 157 cm chest for a person filmed from below (screen low/tilted back, so the belly bulged toward the lens and the fixed strip landed lower on the body) — consistent but wrong. So (a) the face model's head-pitch (`facePitchDeg`, from `outputFacialTransformationMatrixes`) must be within −8°…+12° (`MIN_PITCH_DEG`/`MAX_PITCH_DEG`) or the popup shows "the camera is looking up/down at you" and the **Camera level** check is red; on six real frames of one person, ordinary scans read 3°, 7°, 9° while the scans that went wrong read 15°, 19° and −11° (the from-below one). It is a heuristic from six data points, and head pitch and camera pitch are conflated. (b) A chest estimate outside 70–145 cm is refused ("That measurement doesn't look right") rather than shown. If the pitch matrix is unavailable the check is skipped.
  - **Checklist:** while scanning the popup shows five live checks — Face, Camera level, Shoulders, Chest in view, Arms clear — each ✓ / ✕ / •, next to the guidance line, so a stuck scan shows which requirement is blocking it.
  - **Diagnostics:** while scanning, the popup shows distance, face px, iris px, live shoulder/torso cm and steadiness (±%), and if anything throws, the error text — so a failing scan says why.
  - **Privacy:** everything runs on-device; no frames are uploaded, and the result lives in memory only (`fit/bodyProfileStore.ts`, no `localStorage`) — forgotten on reload.
  - **Accuracy caveat:** an estimate, plausibly within about one size, **not yet validated against tape measurements**. One real frame showed the iris and face-width scales disagreeing by ~10% (they are blended, but the truth for that person is unknown). Error sources: face-size variation between people, the assumed depth ratio and shoulder→chest regression, camera field of view, loose clothing, slouching, camera tilt. Tunable constants: `FACE_WIDTH_CM`, `IRIS_DIAMETER_CM`, `ASSUMED_HORIZONTAL_FOV_DEG`, `*_PLANE_OFFSET_CM` (`faceScale.ts`); `DEPTH_*`, `CHEST_*`, `TORSO_WEIGHT`, `GIRTH_ADJUST_CM`, `CHEST_UPPER_BOUND_CM` (`sizing.ts`); band/percentile settings (`bodyGeometry.ts`). Charts are chest/bust-based, so only meaningful for tops and dresses; `CartItem` carries no product category yet, so numeric-sized trousers/shoes would be misjudged.
- **Status:** In scope for UI; explicitly requested by the user. No checkout button beyond a disabled/"coming soon" affordance, since there is no order/payment endpoint.

## 6. Profile / Account
- **Purpose:** view (read-only) the same data driving Home's personalization, plus logout.
- **API:** `GET /api/v1/customers/me/summary`, `POST /api/v1/auth/logout`.
- **Status:** In scope, small.

## 7. Wardrobe / Virtual Try-On
- **Purpose:** a lightweight styling toy — pick from a small hardcoded t-shirt catalog and preview it live on the customer's own camera feed before adding to cart.
- **API:** none — the catalog (`src/screens/TryOn/tshirts.ts`) and the shirt artwork are both hardcoded/generated client-side (see Gap #4 below); this is not the chat-driven discovery flow and doesn't call `/api/v1/chat`. The camera feed never leaves the browser — nothing is uploaded, recorded, or sent to any endpoint.
- **Content:** grid of t-shirt thumbnails (color/pattern only, no photos — rendered as inline SVG); a preview panel (`CameraTryOn.tsx`) that requests the device camera via `getUserMedia`, runs client-side body-part segmentation each frame (TensorFlow.js BodyPix, ResNet50 — `bodySegmentation.ts`) to find which pixels are the customer's actual torso/upper-arms, and draws a fully designed fill — the selected tee's color/pattern plus deliberate gradient/fold shading, not sampled from the video (`drawGarmentFill.ts`) — fully opaque, clipped to that exact shape. An earlier version blended the fill with the backdrop's real luminance so folds would look "real," but that let the customer's actual shirt texture/pattern show through no matter how much it was pre-blurred and still read as a flat patch; full replacement removes that tension since nothing of the real garment can leak through a fill that isn't derived from the video at all. Real-time tracking still comes from the live segmentation, so it follows the customer's actual shape/motion — the trade-off is only being able to redraw a garment that's already there (it can't add a shirt where there is none, or change a collar/sleeve shape); graceful fallback states for permission-denied, no-camera-found, no-person-in-frame, and generic errors; "Add to cart" using the same `CartRepository` as Chat/Cart.
- **Status:** In scope — explicitly requested by the user as a standalone feature, separate from the out-of-scope full product catalog below.

## 8. Session/Error boundaries
- **401 / session-expired interstitial:** any API call returning 401 clears the token and redirects to Login with a "your session expired" message.
- **Generic error state:** for 500s (`ErrorResponse`), show retry affordance; surface `trace_id` in a "details" disclosure for support/debugging.
- **Status:** In scope (cross-cutting, not a distinct route).

## Explicitly out of scope for this phase (flagged, not built)
- **Full product catalog/browse/search screen** — no list/search endpoint exists; discovery of real, purchasable stock only happens through chat. (The Wardrobe/Try-On screen above is a separate, hardcoded styling toy — it is not this.)
- **Order history / checkout** — no order or payment endpoints exist.
- **Session history list** ("all my past conversations") — the contract has `GET /sessions/{id}` (single) and `POST /sessions` (create), but no "list my sessions" endpoint. Can revisit if backend adds one.
- **Stylist/Admin consoles** — `AuthUser.role` supports these roles but no screens are designed for them here.
